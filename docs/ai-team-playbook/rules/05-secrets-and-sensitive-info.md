# 规则 05：敏感信息与密钥纪律

> 一次泄露，终身作废。本篇是签名材料、令牌、密钥的全生命周期规矩，以及泄露后的处置流程。扫描模式见 `checklists/secrets-scan-checklist.md`。

## 一、绝不入库清单（红线）

以下任何一项**永远不得**出现在：版本库任何分支与历史、源码分发包、文档、评论、日志、记忆文件、构建产物中：

- 签名材料（签名文件、签名密码、证书指纹）；
- 访问令牌、PAT、API Key、密码、私钥；
- 指向这些秘密的**存放位置指引**（文档里连「去某某地方取」都不写——那等于给攻击者画地图）。

## 二、签名材料规矩（CatGame 真实教训换来的）

背景：旧签名材料与明文密码曾随源码包分发导致泄露。处置与后续规矩（详见 `cases/case-catgame-01-signing-leak.md`）：

1. **泄露即作废**：旧签名身份永久作废，换新签名重新签发。不换签名的后果：任何拿到旧材料的人都能以你的身份发布应用。
2. **签名材料单独离线保管**，永不进源码包、永不进版本库——与「绝不入库清单」一致，单独强调是因为签名文件长得像资源文件，最容易被顺手打包。
3. **签名配置走环境变量**，且配置文件加进 gitignore——构建脚本读环境变量，仓库里连变量名对应的值都没有。
4. **发布前双扫**：本地仓库 + 远端 tarball 各扫一次（签名材料文件特征、密码、令牌），零命中才发布。只扫本地不够——远端可能躺着历史提交里的残留。

## 三、令牌使用规矩

- 凭据只在当次上下文以受控方式传递，**不写入任何长期留存处**——长期记忆、文档、会长期留存的交付物一律不写。
- 令牌失效（401）才重新索取；有效时反复索要新令牌只会扩大暴露面。401 后按流程报告并索取，不反复重试旧令牌。
- **出现在评论、聊天记录、日志等半公开面即视为泄露，立即吊销重发**，不评估「应该没人看到」。
- 最小权限：只申请当前任务需要的 scope，用完即弃优于长期持有。

## 四、泄露应急处置（发现即执行，不等裁决）

1. 立即吊销/轮换该凭据（先止血，比查清楚重要）。
2. 相关身份作废（签名则换签名，令牌则换新令牌）。
3. 排查暴露面：该凭据出现在哪些渠道、各自被谁可见。
4. 修订流程堵住来路（本次泄露是怎么发生的——打包脚本？粘贴？——把那个动作变成禁令或自动化检查）。
5. 记录教训进案例库（脱敏后），让规矩有出处。

## 五、写文档/交付物时的脱敏义务

对外发布任何文档（包括本手册这类经验总结）前：

- 按 `SENSITIVE-INFO-AUDIT.md` 的 grep 模式全量扫描，零命中。
- 案例叙述只保留**技术事实与流程事实**：「签名材料曾随源码分发导致泄露 → 重做签名并立下永不入库规矩」是合格表述；出现具体文件名、路径、平台内部编号、人名邮箱就是废稿。
- 内部平台链接、内部任务编号、成员标识一律不出现。
- **署名口径**：公开仓库的归属信息（仓库所有者账号、项目公开域名）允许保留——发布渠道即该账号，属公开事实；但姓名、邮箱、手机号等个人信息禁止出现。写扫描清单时把这条口径写清，避免「禁止个人信息」与「保留公开仓库归属」字面打架。

## 六、验证方式

- [ ] 发布前本地 + 远端双扫零命中（有命令输出为证）。
- [ ] 仓库与分发包中无任何签名材料、令牌、密钥。
- [ ] 签名配置全部来自环境变量，gitignore 覆盖配置文件。
- [ ] 半公开渠道出现过的凭据已吊销（有吊销记录）。
- [ ] 对外文档经敏感信息自查清单扫描。
