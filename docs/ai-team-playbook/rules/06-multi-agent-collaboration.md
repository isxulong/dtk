# 规则 06：多智能体协作与任务链纪律

> 本小组是多个 AI 成员在任务编排平台上协作。本篇是任务链编排、巡检、阻塞判定的规矩——来自真实的「3 小时停滞没人发现」事故。

## 一、任务链的标准形态

复杂工作拆成**自动接力的任务链**，而非一个大任务从头跑到尾：

```
方案（对抗）→ 实施 → 独立质检 → 推送+线上核验
```

- 每段一个任务，用依赖关系串起来（上游完成自动解锁下游）。
- 每段任务书写明：必读材料（给精确出处）、验收点（写死、可核查）、交付物格式。
- **巡检伴随任务链启动**，推送收口后自动停用——巡检的生命周期跟着项目走，不空转。

## 二、实质巡检（不是表面巡检）

**规则**：巡检每轮必须做实质检查，不是看一眼任务状态就走。三件事：

1. **看执行记录**：任务当前是否有正在运行的轮次（有 = 正在干活，不打扰）。
2. **看活动**：最近一个时间窗内有没有新评论、新交付。
3. **看依赖**：显示「阻塞」但只是在等上游 = 正常排队，不算异常。

**为什么（真实事故）**：曾用某定时触发通道做巡检，累计触发 15 次、全部停在排队状态一次都没真正执行——通道级故障，表面显示「已设置定时」完全正常，实际全程空转。那 3 个多小时的任务停滞没有任何一轮巡检真正看过。**教训：巡检通道本身要先验证可用（触发后确认真的执行了），并且巡检要看实质内容，不看表面状态。**

## 三、阻塞判定标准（三个条件同时满足才是真阻塞）

- **45 分钟零活动**（无新评论、无交付物）；
- **无运行中的轮次**；
- **无排队中的依赖**（不是在正常等上游）。

三条同时成立才判定阻塞并介入；只中一两条是正常推进或正常排队，不打扰。

## 四、「假完成」模式识别与处置

**模式**：成员跑满单轮运行次数上限后被平台自动收尾，任务状态却仍显示「进行中」——看起来在推进，实际已停。

**处置**：巡检识别到「假完成」后**原地续跑**（保留上下文接着跑），不是新建任务重来。新建任务会丢失上下文，让成员把已经做完 95% 的活重新理解一遍。

**预防**：任务书把收尾动作（修最后的断言、重跑测试、上传产物）明确列出，成员被收尾前更可能留下可接续的现场。

## 五、协作沟通纪律

- 用户的口径变更，**判断后完全执行**：用户说「这个阶段你可以分析判断而非完全认可，但在作出决定后要完全认可并执行」——裁决前充分论证（含推翻用户建议的勇气），裁决后不打折扣执行。
- 实测压过剖析推断：剖析报告里的理论问题，用户拿真机/真实打印件否了就撤销，不坚持「报告里写了就要修」。
- 进度汇报含实质：当前百分比 + 卡点 + 原因 + 下一步，不写「一切正常」。
- 阻塞与异常**主动上报**，不等用户来问「为什么阻塞二没有及时发现」。

## 六、验证方式

- [ ] 任务链每段有明确验收点，依赖关系正确（上游完才解锁下游）。
- [ ] 巡检通道经过「真的执行了」验证，不是只显示已设置。
- [ ] 巡检每轮查三件事：运行中轮次、活动窗口、依赖排队。
- [ ] 阻塞判定按三条件，误报率为零（没在正常推进时打扰）。
- [ ] 出现停滞时能区分「假完成」并原地续跑。

## 真实出处

- 15 次巡检空转与假完成：dtk 20 条缺陷修复轮（2026-10-14），本篇全部规矩的直接出处。
