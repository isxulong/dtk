# 规则 03：测试、验收与风险预审

> 本篇回答：测试写到什么程度算够、独立质检怎么做才算独立、验收口径怎么定、方案实施前为什么要先审「它会怎么出错」。

## 一、量化口径先于修复（先定及格线，再动手）

**规则**：任何「优化」「修复」「提速」类工作，动手前先把验收口径写成可测量的数字，并写进任务书。

**真实口径（dtk 项目，可直接复用或按同法重测）**：
- 大文本渲染：2000 字 ≤ 500ms；5000 字 ≤ 1500ms，且耗时曲线近线性。
- 冷启动首格可见：≤ 1.5s（Fast 4G 实验线）——同时**诚实声明**「HTML 必回源那段时间前端无法消除，不承诺 <1s」。
- 性能优化收益必须同路径 A/B 实测，不接受「理论应该快了」。

**为什么**：dtk 曾凭直觉判断「O(N²) 瓶颈在网格重建」，真实瓶颈却是 innerText 强制 reflow——没有量化口径和测量，优化会打在错误的靶子上（5000 字从 34 秒到 125ms 的修复，改的是一个属性读法，不是重构）。详见 `cases/case-dtk-03-innertext-reflow.md`。

## 二、不变量写进测试（比功能断言更硬）

**规则**：对「变换类」功能（格式化、排版、归一化），把以下不变量写成自动化测试，与功能断言同级：

- **零内容丢失**：处理前后剥离空白与指令后，可见字符序列逐字节一致。
- **幂等**：二次执行输出逐字节不变；零改动时不产生副作用（如撤销栈垃圾）。

**做到什么程度算够**：不变量测试与功能测试一起进 CI；质检官用**自建样本**（不是实现方的用例）复证——一键排版验收时质检官自建 8 组样本 + 47.6 万字符脏样本独立复证零丢失与幂等。

## 三、独立质检三段论

**规则**：实现、质检、推送由不同角色（或至少不同轮次、干净环境）完成；质检结论三态：**通过 / 有条件通过（列条件）/ 不通过（列 P0/P1/P2 阻断项）**。

质检的「独立」必须体现在：

1. **换干净目录重跑全量测试**（不用实现方的运行环境残留），条数与实现方对照。
2. **自建探针与自备样本**，不接受实现方自述：双击定位修复后，质检官用独立探针对 85 个格子逐格双击验证零漂移；标点规则用**两套独立实现的引擎逐格对账**（双引擎对账法）。
3. **对抗性验证门禁**：故意破坏（改错版本号 / 删一条 preload / 改双源数据一字），确认测试立刻红——门禁有效性本身也要验证。
4. **回归面逐字节比对**：明确「零改动」承诺的区域（如打印样式），与上一版本逐字节比对，不看 diff 摘要。
5. 已知遗留如实披露并分级，不润色（「键盘直输 emoji 未拦截，刷新后自动修正，建议后续补兜底」这种写法是合格的）。

## 四、风险预审（方案定稿后、实施前，强制环节）

**规则**：任何对抗定稿的方案，实施前先派**两路独立风险审查**——实现层失败模式（什么条件下出错、用户看到什么）+ 方案层风险（架构侵蚀、兼容性、回滚）。抓到的每个 P0 必须转化为：规避设计 + 写进实施任务书的硬性验收项 + 自动化测试门禁。

**为什么（真实战绩）**：白屏方案定稿后，风险预审抓到 6 个方案自带的 P0 错误面——每一个不修都会把「白屏」换成更伤信任的新故障：

| 方案项 | 自带错误 | 规避 |
|---|---|---|
| 加载看门狗 | 写进模块里会随模块一起死，兜底形同虚设 | 独立经典脚本放 head，模块末尾设就绪标志 |
| 失败重试 | 重新初始化会挂双份监听器，粘贴文本翻倍 | 重试只允许整页刷新 |
| 范文写进 HTML | JS 就绪前用户打的字会被初始化覆盖——静默丢字 | init 改三态语义，与范文落 HTML 同批上线不得单做 |
| 版本号 12 处同步 | 漏一处 + 一年缓存 = 新旧模块混血，最长一年不可自愈 | version-sync 测试门禁 + 一键 bump 脚本 |
| 范文双数据源 | HTML 与 JS 两份静默漂移，测试全绿也照漂 | 双源逐字节比对测试 |
| init 迁移 | 丢异常保护则全部按钮变死键 | 按钮挂载移到 init 之前 + 保留 try/catch |

完整叙事见 `cases/case-dtk-06-risk-pre-review.md`。

**成本参照**：预审的代价是把「约 20 行改动」变成「小改动 + 一组测试门禁」——远小于任何一条 P0 上线后的代价。

## 五、测试规模的参照系（dtk 真实数字）

- 单个功能（一键排版）：新增后全量 172 条（单测 + E2E）全绿才算完成。
- 一次修复轮次（白屏优化）：187 条（88 单测 + 99 E2E）换干净目录重跑。
- E2E 关键用例要覆盖「反例」：存档三态（含清空→刷新→范文回归）、「格子出现早于 load 事件」、就绪前输入保留。

## 六、验证方式

- [ ] 每个「优化」任务书里有量化口径数字。
- [ ] 变换类功能有零丢失 + 幂等两条不变量测试。
- [ ] 质检报告含：干净目录重跑证据、自建探针结果、三态结论。
- [ ] 测试门禁经过故意破坏验证。
- [ ] 方案实施前有风险预审清单，P0 全部转化为验收项。
