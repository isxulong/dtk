# 反模式集：不要这样做（每条都有真实后果）

> 负面清单比正面规则好记。每条 = 反模式 + 真实后果 + 正确做法（指向规则）。出处均为本小组真实项目经历。

## 对抗与裁决

**❌ 凭直觉定性能根因，不测量就重构**
后果：dtk 大文本卡顿，直觉判断「O(N²) 在网格重建」——真凶是 innerText 强制 reflow，改一个属性读法 5000 字从 34s 到 125ms。按直觉动手就是一次打在错误靶子上的大重构。
✅ 先测量后归因，量化口径先于修复（`rules/03` 第一节）。

**❌ 拿估算基线算收益**
后果：白屏对抗中一方基线「估 4~8s」，实测（更差路径）只有 1.6~2.9s，虚高 2~3 倍，收益计算全盘失真，被找茬当场否决。
✅ 基线必须实测；估算显式标注（`rules/02` 第一节）。

**❌ 实验臂捆绑多变量，宣称单变量结论**
后果：蓝方「-54% 单变量」被红方用蓝方自家瀑布数据证伪——是两项优化的联合效果，归因被迫公开修正。
✅ 一次实验只动一个变量；无法分离时如实写联合归因（`rules/02` 第三节）。

**❌ 对抗中和稀泥、找茬回「总体同意」**
后果：分歧不收敛，裁判无米下锅，对抗空转。
✅ 逐条三态（成立/存疑/不成立），裁判每点选边或给第三种表述（`rules/01`）。

**❌ 对抗无限循环不收口**
后果：边际收益趋零还在转，工期被耗光。
✅ 每轮给收敛判定，超 3 轮主裁决人按证据强制收口（`rules/01` 第三节）。

**❌ 实测与文档冲突时静默按实测交付**
后果：文档里的错值继续存活，误导下一个人（「span 232 笔误」事件）。
✅ 按可复现真实值交付 + 双处披露 + 文档批注订正（`cases/case-catgame-02`）。

## 测试与实施

**❌ 质检用实现方的用例和环境**
后果：实现方的盲区就是质检的盲区，「全绿」是同一套错误自我印证。
✅ 干净目录重跑 + 自建探针 + 自备样本（85 格探针、47.6 万字符脏样本）（`rules/03` 第三节）。

**❌ 自己测自己（单引擎自证）**
后果：排版规则逻辑错会在实现和测试里一起错，永远测不出来。
✅ 双引擎独立实现对账（`cases/case-dtk-01`）。

**❌ 抽验定位 / 规则类逻辑**
后果：抽样通过的错位会漏网到真机用户手上——定位类功能偏 1 格就是事故，抽 10% 看不出来。
✅ 定位 / 规则类逻辑全量验收：85 格逐格探针零漂移、标点禁则成对穷举（`rules/03` 第三节、`cases/case-dtk-02`）。

**❌ 兜底机制写进它要兜底的对象里**
后果：看门狗写进 ESM 模块，模块挂起时看门狗跟它一起死——兜底形同虚设。
✅ 兜底独立部署（经典脚本放 head），与被看守对象不同生死（`cases/case-dtk-06`）。

**❌ 「重试」实现为重新初始化**
后果：监听器挂双份，一次粘贴文本插入两遍——修复手段制造新故障。
✅ 重试只允许整页刷新（`cases/case-dtk-06`）。

**❌ 自动化判定「宁可误判不可漏判」**
后果：误判伤内容伤信任，比漏判（用户手动补一行）代价高一个量级。
✅ 多特征评分 + 判不中回落安全路径并告知用户（`cases/case-dtk-04`）。

**❌ 用整行豁免换取幂等**
后果：豁免段首指令/标题身份时把行内内容一并豁免，用户编辑后再排版时脏污（空格、全角空格、Tab）永久残留，而幂等测试全绿给出虚假安全感。
✅ 豁免粒度收窄到指令 token 与身份本身，内容区照常清理；幂等不变量改为「对规范化后的文本幂等」，并把含脏样本纳入幂等测试（dtk 一键排版 R10/R11 豁免收窄，20261017a）。

## 发布与协作

**❌ 推送后只看平台「部署成功」绿勾**
后果：缓存头配错、版本漂移、新旧混部全都显示「成功」。
✅ 三段验证：敏感扫描 → 逐文件远端逐字节比对 → 线上 curl/浏览器实测核验（`rules/04` 第一节）。

**❌ 把签名材料/令牌打进源码包、写进文档**
后果：CatGame 签名泄露 → 旧身份永久作废、全部重签——一次泄露终身作废。
✅ 永不入库清单 + 环境变量 + 发布前本地/远端双扫（`rules/05`）。

**❌ 巡检只看任务表面状态**
后果：某定时通道 15 次触发全部排队空转、表面「已设置」一切正常，任务停滞 3 小时无人发现；成员跑满轮次上限被自动收尾但任务仍显示「进行中」（假完成）。
✅ 实质巡检三件事（运行中轮次/活动窗口/依赖排队）+ 阻塞三条件 + 假完成原地续跑（`rules/06`）。

**❌ 清理仓库时顺手删「没用的旧文件」**
后果：删部署配置 = 部署失去配置源；删历史版本 JS = 长缓存里的旧 HTML 引用落空，线上白屏。
✅ 删文件前排查隐性引用方（缓存/外链/部署平台/历史版本），查不清就留着（`cases/case-gym-01`）。

**❌ 为了「用户可能担心」而加赘余设计**
后果：用户担心排版耗时，若加等待弹窗——实测 0.12ms/2781 字，担心的场景根本不存在，弹窗是纯负资产。
✅ 用实测数字回应担忧，不用 UI 迎合担忧（`cases/case-dtk-04`）。

**❌ 把「慢」当「死」，误杀还在正常推进的任务**
后果：长任务或正常排队的任务被误判为停滞、遭人为介入甚至杀掉，进度与上下文白费。
✅ 阻塞三条件同时满足才介入：45 分钟零活动 + 无运行中轮次 + 无排队依赖；只中一两条是「慢」不是「死」（`rules/06` 第三节）。

**❌ 新建任务来「重启」一个有上下文的停滞任务**
后果：重开等于全部重做——成员要把已经做完 95% 的活重新理解一遍，上下文全丢。
✅ 假完成原地续跑，保留上下文接着跑（`rules/06` 第四节）。

**❌ 内部口径与用户口径冲突时自作主张**
后果：要么按内部理解硬顶用户造成无谓返工，要么擅自放行导致已发布构建作废（CatGame 教训）。
✅ 先把用户原话核实并落档 → 交裁判裁决 → 按裁决执行（`rules/02` 第四节、`cases/case-catgame-02`）。
