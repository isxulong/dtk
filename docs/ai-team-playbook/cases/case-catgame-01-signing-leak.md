# 案例 CatGame-01：签名材料随源码分发导致泄露

> 项目：[CatGame 猫抓游戏](https://github.com/isxulong/CatGame)（Android WebView）。本案例是敏感信息纪律（`rules/05`）的直接出处。
>
> 锚点说明：该历史事故的 commit 哈希、版本号与上线日期在可核素材中未提供；为遵守证据口径，本篇不补造锚点。

## 背景

Android 应用发布需要签名。签名材料（签名文件 + 密码）就是应用的身份——谁持有它，谁就能以你的名义发布应用。

## 当时发生了什么

旧签名材料与**明文密码**曾随源码包一起分发——签名材料被打包进了本该只含代码的包里，导致泄露。

## 怎么裁决（处置动作，顺序即纪律）

1. **旧签名身份永久作废**——不换签名的后果是：任何拿到旧材料的人都能以你的身份发版，这个风险不会因时间衰减。
2. 换新签名，重新签发。
3. 立下四条永久规矩：
   - 签名材料**单独离线保管**，永不入源码包、永不入版本库；
   - 签名配置走**环境变量**，配置文件加 gitignore；
   - 发布前敏感信息**双扫**：本地仓库 + 远端 tarball 各扫一次（签名材料文件特征、密码、PAT），零命中才可发布；
   - 教训脱敏后写入案例库，让规矩有出处。

## 沉淀的规则

1. **签名材料长得像资源文件，最容易被顺手打包**——打包脚本和分发流程要显式排除，不能靠「记得别放进去」。
2. **密码与文件不分离等于没分离**：签名文件和明文密码放在同一个分发包里，一层防护都没有。配置进环境变量，仓库里连值都没有。
3. **只扫本地不够**：远端可能躺着历史提交里的残留——本地 + 远端 tarball 双扫。
4. **泄露即作废，不评估暴露面大小**：「应该没人下载过」不是不换签名的理由。先止血（作废换新），再排查。

## 这条规则后来怎么用

- 「发布前本地 + 远端双扫零命中」固化为全部项目（dtk/lydz/Gym）发布清单的固定一项，见 `checklists/secrets-scan-checklist.md`。
