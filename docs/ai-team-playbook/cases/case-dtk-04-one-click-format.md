# 案例 dtk-04：一键排版——四路并行提方案、确定性否决 LLM

> 项目：[dtk 申论格子纸](https://github.com/isxulong/dtk)（2026-10-14 上线，commit f5593f5，版本 20261014f）。从需求提出到上线全程 **1 小时 48 分钟**，是「多路独立提方案 + 主 AD 裁决」模式的标杆战例。

## 背景

用户提出新需求：从别处复制的文本常缺排版指令（+N+）、带多余空格，需要手动调整，想要「一键排版」按钮。用户给了初步想法但明确说「不局限于我的思路……组织更多人员开动思路尽可能提出不同方案」。

## 当时发生了什么（流程拆解）

| 阶段 | 用时 | 做了什么 |
|---|---|---|
| 方案设计 | 18 分钟 | 产品 / 架构 / 高级开发实证 / 原型交互**四路并行**独立提方案 |
| 口径确认 | 33 分钟 | 两轮问答（空格规则、居中公式、按钮位置），主要等用户回复 |
| 实现 | 24 分钟 | auto-format 模块 + 按钮接线 + 172 条测试全绿 |
| 独立质检 | 24 分钟 | 干净目录重跑 + 自建探针复证，一次通过无返工 |
| 推送上线 | 7 分钟 | 敏感扫描、逐文件比对、README 同步 |

四路方案**高度收敛**后由主 AD 裁决，关键裁决点：

1. **确定性规则路线，否决 LLM 路线**。理由四条：排版是确定性问题；LLM 输出不可复现、无法进测试体系；引入后端与网络依赖（产品底线是零构建纯静态、离线可用）；隐私场景过不去。处理耗时实测 0.12ms/2781 字，10 万字病态上限也不到 20ms——**用户担心的「等待弹窗」场景在这条路线下根本不存在**。
2. **标题判定「宁可漏判、不可误判」**：多特征评分（9 特征加权）判中才按公式居中——**标题居中公式 ⌊(25−字数)/2⌋**，奇数余量自然留在右侧；判不中回落 +2+ 并明确提示用户。漏判代价是用户手动调一行，误判会伤信任。实测：标题判定 19/19 全对，对抗用例 6/7（唯一失败是 31 字长标题落入安全兜底——恰是设计意图）。
3. **空格的语言邻接规则**：空格有一侧是中文/全角就删（「2026 年」→「2026年」），两侧都是 ASCII 字母数字才保留（「GB/T 15834」「iOS 16」不动）——比无差别全删聪明，正是用户手动调整的痛点根源。
4. **已识别的坑写进任务书**：撤销栈是 400ms 节流写入的，排版前必须先强制冲刷入栈，否则 Ctrl+Z 撤不回排版前——这个坑在方案阶段就被识别并写成硬性实现要求。

## 怎么验证

- 零内容丢失 + 幂等两条不变量写进自动化测试（见 `rules/03`）。
- 质检官自建 8 组样本 + 47.6 万字符脏样本独立复证，不用实现方的用例。
- 用户锁定的六条口径逐条核验（含「GB/T 15834」「iOS 16」这类两侧皆 ASCII 的空格保留、标题居中公式 ⌊(25−字数)/2⌋、奇数余量留右侧、无等待弹窗）；打印样式与双击跳转与上一版逐字节零改动。

## 沉淀的规则

1. **多路并行方案的差异化分工**：产品（场景分类学与取舍）/ 架构（确定性算法）/ 高工实证（替代路线 + 小规模真实实验）/ 原型（交互体验）——视角错开才能真并行，不是四个人写同一份方案。
2. **LLM 适用性四问**：问题是否确定性的？输出要不要可复现进测试？产品形态允许引入后端/网络依赖吗？隐私与离线场景过得去吗——四问答完再决定动不动模型。
3. **宁可漏判不可误判**：自动化判定类功能，误判的代价（伤信任、误伤内容）通常远高于漏判（用户手动补一下）。判不中的回落路径必须设计好并告知用户。
4. **「耗时担忧」用实测回应**：用户担心处理耗时，方案直接用实测数字（0.12ms/2781 字）证明该场景不存在，而不是加等待弹窗迎合担忧。
5. **用户初步想法是候选不是答案**：用户自己提的「不管标题直接空两格」被评估为候选之一，最终方案更优——尊重用户的方式是认真比较，不是照单全收。

## 这条规则后来怎么用

- 「方案 → 口径确认 → 实现 → 独立质检 → 推送」五段计时法成为后续工作的标准节拍器，耗时统计随交付报告给出。
