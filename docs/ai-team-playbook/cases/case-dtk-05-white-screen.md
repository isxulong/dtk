# 案例 dtk-05：白屏对抗全程——瀑布、onload 锁与归因之战

> 项目：[dtk 申论格子纸](https://github.com/isxulong/dtk)（2026-10-15 上线，commit 23a20807，版本 20261015a）。红蓝对抗流程最完整的一次实战：独立分析 → 交叉找茬 → 双裁判 → 终裁 → 风险预审 → 实施 → 质检 → 推送 + 线上核验，从用户反馈到上线约 2.5 小时。

## 背景

用户真机反馈：打开网页长时间白屏——页面框架（标题/工具栏/按钮）能出来，但格子纸区域和默认范文迟迟不出现。站点部署在 Cloudflare，主要用户在国内。

## 当时发生了什么

**第一轮 · 独立分析（红=架构视角，蓝=实证视角）**，双方独立得出、互相印证的结论：

- **渲染层无辜**：400 格 DOM 构建实测仅 6~20ms，双方一致排除——白屏不是代码慢。
- 病灶是**加载编排**：① HTML 每次必回源（Cloudflare 路径实测 0.8~2.5s 波动）；② 58.6KB 的 HTML 全部到齐后才开始抓 5 个 ESM 模块，其中一个还要等另一个抓完（**两级串行瀑布**），每个串行段按网络 RTT 放大；③ 首屏渲染被 `window.onload` 锁住，要等 favicon 和 Cloudflare 挑战 iframe 全部就绪。
- 蓝方同路径 A/B 实测：modulepreload + 去锁后「HTML 到达→格子出现」755ms → 347ms（**-54%**）。

**第二轮 · 交叉找茬（本案例最精彩的部分，三条经典）：**

1. **红方抓到蓝方实验设计错误**：蓝方宣称「单变量实验 -54%」，红方用**蓝方自己报告里的瀑布数据**证明该实验臂捆绑了 modulepreload 和去锁两个变量——-54% 是联合效果，归因必须改。蓝方认账修正。
2. **蓝方抓到红方基线虚高**：红方「现状白屏 4~8s（Fast 4G）」的基线，被可复现实测 1.6~2.9s（还是更差网络路径）否决——虚高 2~3 倍，同向虚高的定量主张共三处。红方认账。
3. **双方数据共同确立硬依赖**：蓝方数据反证了「只加 preload 不拆 onload 锁，首屏一毫秒都不改善」——确立改动顺序的硬依赖：onload 锁稳态只值 ~0.1s，但它是**必须第一个拆的锁**，不拆它其它优化收益全被锁在后面。

**第三轮 · 双裁判**：技术向 + 产品体验向两位裁判互不通气独立裁定。两位裁判一致补入一条**双方都漏的**：模块请求挂起时页面没有任何超时/重试兜底——挂起就永远停在白屏状态（用户截图的「特别久」症状，最可能的解释之一就是它）。

**终裁结论（一句话根因）**：页面不是代码慢，是「内容被设计成等好几个网络包裹全部到货才摆上架」。修复第一批四项必须同批：拆 onload 锁、modulepreload×5、范文直接写进 HTML、加载超时+重试兜底；第二批静态资源一年期缓存。**明确不做**：内联模块（收益与 preload 重复，白背维护债）、格子虚拟化（无优化空间）、版本号按文件粒度 bump（一年缓存下漏 bump 不可自愈）。

## 上线结果

- 质检独立复测：「HTML 到达→首格」646ms → 344ms（-46.7%，与 -54% 同量级），首格出现不再等 load 事件（首格 89ms vs load 2043ms）。
- 187 条测试（88 单测 + 99 E2E）干净目录重跑全绿；推送 16/16 逐字节比对；线上 curl 核验五项全过。

## 沉淀的规则

1. **诚实口径**：终裁写「冷启动首格 ≤1.5s（Fast 4G 实验线），不承诺 <1s——HTML 必回源那段时间前端无法消除」。收益数字带归因边界（-54% 是联合效果），边界外的事明说做不到（国内→Cloudflare 真实路径测试环境复现不了，需真机回归）。
2. **「必须第一个拆的锁」**：一个稳态收益很小（~0.1s）的改动，可能是其它所有优化的前置条件——评估改动要看它在依赖链上的位置，不只看它自己的直接收益。
3. **交叉找茬的三板斧**（全部真实命中）：用对方数据证伪对方、实测否决估算基线、用数据确立改动顺序硬依赖。
4. **裁判要补双方盲区**：对抗双方都漏掉的东西（超时兜底）由裁判补入——裁判不是只裁判已有方案。
5. **加载问题的分段排查法**：网络/CDN → 模块瀑布 → 模块求值 → DOM 构建，逐段实测排除，不猜。
