# 案例 dtk-01：标点「偷格子」——按国标重写占格规则

> 项目：[dtk 申论格子纸](https://github.com/isxulong/dtk)（2026-10-13 上线，commit f1355d6；版本号素材未提供，不补造）。本案例是「红蓝对抗优化」全流程的第一次完整实战。

## 背景

申论考试答题卡一行 25 格，标点占格有严格规范，写错在真实考试中会判违规。dtk 是在线模拟格子纸，排版引擎的占格规则必须和真实答题卡一致。

## 当时发生了什么

旧引擎把逗号、句号等点号**无条件挤进前一格**——每个点号偷一格，这不是行末边界处理。一段文字下来能「偷」出好几个格子的余量，和真实答题卡的排版完全不同，用户拿它练习等于在练错误的排版习惯。

## 怎么发现与怎么裁决

红蓝对抗流程（AB 分别设计方案 → 交换找茬 → 双裁判独立评判 → 主 AD 终裁 → 实施 → 独立质检 → 推送）中定稿的规则口径：

- 团队定稿口径全文：**「默认独占一格、写满 25 格才与末字同格、绝不落行首」**（依据 **GB/T 15834—2011**《标点符号用法》与申论通行口径）；
- 行末同格只在已写满 25 格时发生，是规范允许，不算偷格；
- 「绝不落行首」即避头规则；
- 对抗中还揪出三个同类缺陷一并修复：弯引号 “”‘’ 漏判（旧规则只认直角引号）、叠用标点（？！）挤格、直引号落行首。

行末同格的格子最初用淡黄底标注提示「考试允许」——**后续真机反馈认为多余**（「这是很自然的排版不需要提醒」），按用户口径去除，见 `case-dtk-02` 的姊妹教训：裁判方案也要让位于真机感受。

## 沉淀的规则

1. **领域规则必须锚定公开标准**：占格这种有国标（GB/T 15834—2011）的事，不发明自己的规则，按标准实现并在文档注明依据。
2. **排版引擎独立成模块 + 自动化测试**：这次 bug 的温床是「改代码没法回归」——引擎抽成独立模块，配 26 条单测 + 28 条 E2E。
3. **双引擎对账质检法**：质检官用**两套独立实现的引擎**逐格对账复核全部 17 组用例——同一套代码自己测自己，逻辑错会两边一起错、测不出来；独立实现互为参照。
4. 同批修复了预设文本换行问题（「+2+ 指令本身不含换行」——指令语义要读真实代码确认，不能凭直觉）。

## 这条规则后来怎么用

- 验收口径「预设文本计数 382、2000 字渲染约 90ms（远低于 500ms 门限）」成为后续所有性能工作的基线参照。
- 「双引擎对账」固化为排版类改动的标准质检动作。
