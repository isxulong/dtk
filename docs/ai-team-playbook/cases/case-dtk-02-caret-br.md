# 案例 dtk-02：双击定位偏移——遍历逻辑的元素盲区

> 项目：[dtk 申论格子纸](https://github.com/isxulong/dtk)（2026-10-13 上线，commit adb0a17；版本号素材未提供，不补造）。真机反馈驱动的一次根因修复。

## 背景

dtk 支持双击格子跳转到输入框对应文本位置——这是核心交互，此前测试覆盖 175 个测试点零偏移。

## 当时发生了什么

用户真机反馈：双击定位**前文正常、后文比真实位置靠后**，越往后偏得越多。

## 怎么发现

「越往后偏得越多」这个规律本身就是线索——偏移量随位置**累积**，说明每经过某种元素就漏数一次。根因：存档恢复/导入文本时换行会变成 `<br>` **元素节点**，而旧的定位函数 `setCaretToPosition` 只遍历**文本节点**，把 `<br>` 跳过去了——每经过一个换行，光标就偏后 1 格。

修复：重写为 `findCaretPoint`，把元素节点纳入遍历。

## 怎么裁决与验证

- 质检官用**独立探针**对 85 个格子逐格双击验证，零漂移——不是实现方自报「修好了」。
- 26 项单测 + 37 项浏览器实测全绿。
- 同一轮顺带按用户口径去除了行末同格的黄色标记（见 `case-dtk-01`）。

## 沉淀的规则

1. **「累积性偏移」是遍历/索引类 bug 的特征指纹**：看到「越往后越偏」，先怀疑每次循环漏数了某类节点/元素，而不是怀疑坐标计算。
2. **DOM 遍历必须同时考虑文本节点与元素节点**：`<br>`、`<img>` 这类「非文本但占位」的元素是遍历逻辑的盲区高发区。
3. **测试点通过 ≠ 真机路径通过**：此前 175 个测试点零偏移，但测试数据没覆盖「存档恢复产生 `<br>`」这条真实路径——测试样本要覆盖全部数据来源（手输、粘贴、导入、存档恢复）。
4. 真机反馈修复的验收必须是**独立探针逐格验证**，不接受实现方自述。

## 这条规则后来怎么用

- 「输入边界」概念在后续一键排版中扩展为「三边界归一化」：粘贴、导入、存档恢复三条路径统一过归一化模块，测试各边界独立覆盖。
- 质检的「独立探针」做法固化为定位/渲染类修复的验收标配。
