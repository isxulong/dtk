# 案例 dtk-03：性能根因误判——真凶是 innerText 强制 reflow

> 项目：[dtk 申论格子纸](https://github.com/isxulong/dtk)（2026-10-14 上线，commit 23a50d5，版本 20261014e）。「全面剖析 → 20 条缺陷修复」轮中最有教学价值的一条。

## 背景

dtk 全面剖析（双方独立分析 + 第三方整合）产出 20 条问题清单，其中一条 P1：大段粘贴渲染变慢——4000 字要约 9 秒。

## 当时发生了什么

直觉判断：O(N²) 瓶颈在**网格重建**——400 个格子 DOM 随文本增长反复重建，听起来合情合理。如果按这个判断动手，就是一次大重构（分帧、虚拟化、增量渲染）。

真实测量后：**真凶是 `innerText` 强制同步 reflow**。每次读取 innerText，浏览器都要先完成布局计算才能给出「渲染后的文本」，在循环里读它就变成 N 次全量 reflow。改成读 `textContent`（纯 DOM 数据、不触发布局）后：

- 5000 字渲染：**34 秒 → 125 毫秒**（约 270 倍）；
- 一个属性读法的改动，不是重构。

## 怎么裁决

- 先修测试口径再修性能：验收数字写死——**2000 字 ≤ 500ms、5000 字 ≤ 1500ms 且耗时曲线近线性**。
- 修复后实测：2000 字约 85ms、5000 字约 150~180ms，原卡顿消除。
- 52 条单测 + 78 条 E2E 全绿，换目录重跑同样全绿。
- 同轮的反例也很有价值：emoji 问题原计划做「码点化重构」（动渲染核心、最高风险），用户一句「申论答题卡本就不该出现 emoji」点醒——直接在输入边界**拒绝输入**，引擎一行不动，风险从最高降到低。**最优雅的修复是让问题消失，不是把问题修对。**

## 沉淀的规则

1. **性能优化先测量、后归因**：「听起来像瓶颈」和「测量出的瓶颈」经常不是同一个。动手重构前必须有 profile/计时数据，优化打在错误的靶子上比不优化更贵。
2. **量化口径先于修复**（铁律 5）：没有写死的验收数字，就没有「修好了」的定义。
3. **innerText vs textContent**：读渲染后文本（要考虑换行/隐藏的语义）才用 innerText，且只在循环外读一次；循环内读文本一律 textContent。同类陷阱：循环内读 offsetWidth/getBoundingClientRect 同样强制 reflow。
4. **先问「能不能不做」**：emoji 案例——把「正确处理 X」换成「边界拒绝 X」，风险降一个数量级。每个高风险修复方案都先问一句：能不能让这个问题不存在？
5. 分批隔离风险：20 条缺陷按「同区域同批、最高风险单独一批」分五批实施，每批全量测试过关再进下一批。

## 这条规则后来怎么用

- 「2000 字 ≤500ms」成为 dtk 后续所有改动的回归门槛。
- 白屏优化时，渲染层被实测排除（400 格 6~20ms）——正是本轮建立的「先测量」习惯，避免了又一轮对渲染层的冤枉重构（见 `case-dtk-05`）。
