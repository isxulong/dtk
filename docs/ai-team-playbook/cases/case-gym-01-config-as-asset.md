# 案例 Gym-01：部署配置即资产——删配置 = 拆部署

> 项目：[Gym 训练动作库](https://github.com/isxulong/Gym)（Cloudflare Workers 部署）。一条短规矩的真实出处。
>
> 锚点说明：该维护隐患对应的 commit 哈希、版本号与上线日期在可核素材中未提供；为遵守证据口径，本篇不补造锚点。

## 背景

Gym 部署在 Cloudflare Workers，部署配置由仓库根的 `wrangler.jsonc` 提供——Worker 名称、路由、兼容日期、资源绑定全在里面。

## 当时发生了什么

项目维护中识别出一个隐患模式：`wrangler.jsonc` 这类部署配置文件**必须随每次推送保留**。如果哪次「清理仓库」把它删了，部署不会立刻报错——但部署从此失去配置源，后续部署行为变得不可预期，而且问题暴露时往往离删除动作已经很远，难以关联。

同类隐患：**历史遗留文件**（旧版本 JS、不再被新代码引用的资源）未经确认不删——dtk 也有同款纪律：旧版本戳的 JS 文件永不删除改名，因为旧 HTML 副本（长缓存、用户本地）可能还引用着它们，删了就是线上白屏。

## 怎么裁决

两条规矩定稿：

1. **部署配置文件与代码同等重要**：随每次推送保留；改动它要走与改代码同级的审查（评估爆炸半径——一条过宽的缓存规则影响的是全站）。
2. **删除文件前先查引用与部署依赖**：查不到引用不等于没有引用（缓存、外链、旧版本、部署平台都可能是隐性引用方）；查不清就留着，磁盘空间比线上事故便宜。

## 沉淀的规则

1. **配置即资产**：部署配置文件进版本库、随推送保留、改动同级审查、删除视同高危操作。
2. **「删文件」的审查标准高于「加文件」**：加文件的错误当场可见，删文件的错误可能潜伏到某个边缘路径才爆发。
3. **隐性引用方清单**（删文件前逐个排查）：长缓存中的旧 HTML、用户本地缓存、外部链接、部署平台配置、历史版本。

## 这条规则后来怎么用

- 「历史遗留文件未经确认不删」写进 `rules/04` 第四节，dtk 白屏优化时明确「js/ 历史文件永不删除改名」进 README 发版纪律。
