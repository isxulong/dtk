# 案例 lydz-01：迭代收敛式对抗流程定稿

> 项目：[lydz 旅游搭子测试](https://github.com/isxulong/lydz)。本案例是「迭代收敛式」对抗流程（`rules/01` 第三节）的定稿出处。
>
> 锚点说明：流程定稿对应的 commit 哈希、版本号与上线日期在可核素材中未提供；为遵守证据口径，本篇不补造锚点。

## 背景

lydz 项目的红蓝对抗不是一次性方案对抗，而是**边做边验的实施迭代**——需要一套能收敛、不空转的多轮流程。

## 当时发生了什么与怎么定稿

多轮演练后定稿的流程：

```
AB 各自落地 → 交叉检验 → C 汇总（必须给「收敛判定」）→ AB 复核 → 未收敛则再循环
```

四条定稿规矩，每条都对应一个真实踩过的坑：

1. **每轮 C 汇总必须显式给「收敛判定」**（已收敛 / 未收敛 + 未决点清单）。没有这个判定，汇总会退化为「把两边的话拼在一起」，对抗永远「还在进行中」。
2. **超 3 轮未收敛，主裁决人按证据强制裁决收口**。对抗不是永动机——3 轮还没收敛说明剩余分歧的证据密度已经很低，继续循环的边际收益趋零，按「可逆性更高 / 风险更小」的选项裁。
3. **实施者回避对抗**。参与落地的人不做本轮对抗的裁判或找茬方——自己审自己，找茬会下意识护短，裁判会下意识放行。
4. **证据门槛 + 逐条三态**（与四段式共用）：文件+行号 / 可复现实验；每条回应只能是「成立 / 存疑 / 不成立」。

## 同一项目沉淀的令牌管理规矩

演练中还定稿了令牌纪律（详见 `rules/05` 第三节）：

- 凭据只在当次上下文以受控方式传递，不写入任何长期留存处（长期记忆、文档、会留存的交付物）；
- 失效（401）才重新索取，有效时反复索要只会扩大暴露面；
- **出现在评论、聊天、日志等半公开面即视为泄露，立即吊销重发**。

## 沉淀的规则

1. **循环必须有刹车**：任何「直到收敛为止」的流程都要定义收敛判定 + 最大轮次 + 强制裁决人，缺一个就是空转流程。
2. **汇总 ≠ 收敛**：合并双方内容只是文书工作，显式判定「收敛了没有、还剩什么」才是汇总的价值。
3. **回避原则**：实施者回避对抗、实现者回避质检——同一个原则的两次应用。
4. 令牌纪律的三条直接进 `rules/05`。

## 这条规则后来怎么用

- 「超 3 轮强制裁决」被写入 `rules/01` 迭代收敛式流程，成为全部多轮对抗的统一刹车。
