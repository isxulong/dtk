# 案例 CatGame-02：「span 277」——证据诚实优于面子

> 项目：[CatGame 猫抓游戏](https://github.com/isxulong/CatGame)。本案例是证据冲突裁决规则（`rules/02` 第四节）的直接出处。

## 背景

CatGame 一次红蓝对抗迭代（版本 v1.4 轮次）：真机反馈 → PM 规格 + A 根因（并行）→ C 合并清单 → 实施 → A/B 双签（B 52/52 断言）→ C 终局裁定收敛。

## 当时发生了什么

对抗中出现一个数值分歧——史称「span 232 笔误」事件：某份材料/文档记载的数值是 **232**，但工程师与两位复核人**三方独立实测一致为 277**。

两种错误处理方式摆在面前：
- 改数据凑文档：把 277 写成 232，表面一致，实际交付错误值；
- 悄悄按实测交付：按 277 交付但不声张——文档里的 232 继续误导下一个人。

## 怎么裁决

**按可复现的真实值 277 交付**，同时：

- **双处披露**：交付物和源文档都写明这个差异；
- 源文档加**批注订正**，把 232 标记为笔误。

原则一句话：**证据诚实优于面子**。三方独立实测一致是最高等级的证据，文档记载在它面前让位；但让位要公开，不要静默——静默修正会让错误记录在别处继续存活。

## 同一轮的姊妹教训：用户口径优先

双签（A/B 双签验收）的阻断项与用户口径冲突时，**用户口径优先**，但走流程：先把用户原话核实并落档 → 再交裁判裁决 → 按裁决执行。这样既不用内部阻断项硬顶用户，也不拿「用户说过」当口头挡箭牌——避免无谓返工与已发布构建作废。

## 沉淀的规则

1. **多方独立实测一致 > 文档记载**（证据优先级，见 `rules/02`）。
2. **实测与文档冲突 = 双处披露**：交付处写差异，文档处加订正，不做静默修正。
3. **用户口径优先但要落档**：用户原话先核实落档再裁决，流程保护双方。
4. 双签的意义就在于抓这种分歧——52/52 断言全绿只是门槛，分歧的裁决质量才决定交付质量。

> 锚点说明：本案例的「B 52/52 断言」与 v1.4 版本信息源自主 AD 持久记忆中的 CatGame v1.4 记录（CatGame 轮次属更早任务链，本手册可及的一手评论未覆盖该数字）；232/277 主干叙事与双方独立起草的案例互证一致。commit 哈希与上线日期素材未提供，故本篇不标注具体提交与上线日期。

## 这条规则后来怎么用

- 「证据优先级表」写进 `rules/02`：可复现实测 > 代码事实 > 用户口径 > 文档记载 > 理论推断。
- dtk 全面剖析中「打印行间隙」理论推断被用户真实打印件否决、从修复范围撤销，是同一原则的复用。
