# AI 研发小组工作经验手册

> 这份文件夹是一支 AI 研发小组在真实项目（公开仓库 [dtk](https://github.com/isxulong/dtk)、[CatGame](https://github.com/isxulong/CatGame)、[lydz](https://github.com/isxulong/lydz)、[Gym](https://github.com/isxulong/Gym)）中沉淀的可复用经验。它的设计目标是：**一个零上下文的新 AI 拿到它，3 分钟内知道自己该遵守什么规矩，每条规矩都能直接执行、并且有办法验证自己做到了没有。** 新加入的人类工程师请按下方「人类读者怎么用」选读。

## 三条元规则（凌驾于所有具体规则之上）

以下三条是全部规则的规则：任何具体规则、任何案例做法与它们冲突时，以这三条为准。

1. **证据先于结论**：没有跑过的命令、测试、实验，不写成「已通过」；理论推测必须让位于可复现实测。
2. **诚实优于面子**：实测数据与既有结论冲突时，按可复现的真实值交付并公开订正，不护短。
3. **敏感信息零妥协**：任何令牌、密码、密钥、签名材料，出现过的场合即视为泄露面，宁可重做也不侥幸。

## 3 分钟上手（新 AI 冷启动动线）

**第 1 分钟：背下十条铁律。** 这是全部经验的压缩包，每条都有完整规则文档可查。

1. **证据门槛**：任何技术主张必须可定位（文件+行号）或可复现（实验方法+实测数字），否则不得进入裁决，更不得写进交付物。→ `rules/02`
2. **对抗不沟通**：红蓝双方独立产出方案，期间互不沟通；交叉找茬必须逐条三态回应（成立 / 存疑 / 不成立），认账修正是义务不是认输。→ `rules/01`
3. **裁判独立、终裁按证据**：双裁判互不通气、通读全部材料后逐项裁定，不和稀泥；终裁按证据不按音量。→ `rules/01`、`rules/02`
4. **实施者回避**：实现、质检、推送三段分离；质检必须用自建探针和自备样本，不接受实现方自述。→ `rules/03`
5. **量化口径先于修复**：先把验收数字写死（如「2000 字渲染 ≤500ms」），再动手修；没有口径不许报「已优化」。→ `rules/03`
6. **实测压过推测**：基线数字必须实测；估算必须标注为估算。实测与文档冲突时按可复现的真实值交付并双处披露。→ `rules/02`
7. **方案定稿后先审错误面**：实施前做风险预审——「这个方案自己在什么条件下会出错」，把抓到的问题转化为规避设计 + 测试门禁。→ `rules/03`
8. **推送三段验证**：敏感信息扫描零命中 → 推送后逐文件远端逐字节比对 → 部署后线上实测核验。少一段不算发布完成。→ `rules/04`
9. **敏感材料永不入库**：签名材料、令牌、密钥不进版本库、不进源码包、不进文档；凡在半公开渠道出现过的凭据一律视为已泄露，立即吊销换新。→ `rules/05`
10. **多处同步的值用机器断言**：版本号、双数据源、成对配置这类「改一处漏一处就出事」的东西，一律写自动化测试门禁，不靠人记。→ `rules/03`、`rules/04`

**第 2 分钟：按你的当前角色跳读。**

| 你正在做的事 | 直接去看 |
|---|---|
| 刚加入、要参与一次红蓝对抗 | `rules/01` → `rules/02` → `checklists/adversarial-review-checklist.md` |
| 要写测试或验收别人的实现 | `rules/03` → `engineering/testing-and-acceptance.md` → `checklists/release-checklist.md` 第 1 节 |
| 遇到性能问题（慢、卡、白屏） | `engineering/performance-diagnosis.md` → `cases/case-dtk-03` / `cases/case-dtk-05` 两个对照案例 |
| 要发布 / 推送 / 部署 | `rules/04` → `checklists/release-checklist.md` 全文勾选 |
| 要接触签名、令牌、密钥 | `rules/05` → `checklists/secrets-scan-checklist.md` |
| 要协调多个 AI 成员跑任务链 | `rules/06` |
| 想看真实战例学套路 | `cases/` 任意一篇，每篇 5 分钟 |

**第 3 分钟：扫一遍反模式集** `anti-patterns.md`。每一条都是「不要这样做 + 真实后果」，是我们踩过坑的负面清单——比正面规则更容易记住。

**动线设计逻辑**（为什么这么组织）：

- `rules/` 是**行为层**——你此刻要做什么就查哪篇，每条规则自带「验证方式」，读完就知道怎么算做到。
- `engineering/` 是**方法论层**——性能诊断、测试验收这类「怎么做才专业」的成套方法单独成册，遇到对应问题可直查，不必从案例中反向归纳。
- `cases/` 是**证据层**——规则不是凭空定的，每篇案例保留完整叙事：发生了什么 → 怎么发现 → 怎么裁决 → 沉淀了哪条规则。想理解一条规则的「为什么」就去翻对应案例。
- `checklists/` 是**执行层**——工作时直接打印/照着勾选，不需要记忆。
- 各层互相引用：规则引用案例作为出处，清单引用规则作为依据，方法论层与规则、案例互链。新 AI 从任何一篇进来都能在两次跳转内到达完整上下文。

## 人类读者怎么用

「3 分钟上手」是给零上下文新 AI 的冷启动动线；人类读者不必按它走，按用途选读即可（每篇规则 / 案例约 5~10 分钟）：

- 想了解「AI 团队怎么做技术决策」：读 `rules/01` + `cases/case-dtk-05-white-screen.md`（最完整的一次对抗实录）；
- 想借用发布与保密纪律：`rules/04`、`rules/05` 与 `checklists/` 可直接移植到任何团队；
- 想做性能优化：先读 `engineering/performance-diagnosis.md`，再看 `cases/case-dtk-03` 与 `cases/case-dtk-05` 两个对照案例（一个真病灶在代码、一个真病灶在网络，方法论相同）；
- 想评估这套手册是否值得引入：先读「三条元规则」与 `anti-patterns.md`——团队的价值观和最常踩的坑都在这两处。

## 使用约定

- **规则条目的固定格式**：`做什么 / 什么时候做 / 为什么 / 做到什么程度算够 / 怎么验证`。看到不符合这个格式的经验描述，它就不是规则，只是故事。
- **案例条目的固定格式**：`背景 → 当时发生了什么 → 怎么发现 → 怎么裁决 → 沉淀的规则 → 这条规则后来怎么用`。
- **数字即口径**：文中所有耗时、阈值、条数都来自当时的真实测量或真实测试记录，可直接复用为验收口径。**性能毫秒数均取自当时的测量环境**（测试机型、网络路径随轮次不同），换项目、换环境时按同方法重测基线，不要照抄数字。
- 本手册只含可复用经验与规则，不含项目流水账；引用的仓库均为公开仓库。
- **署名口径**：公开仓库的归属信息（仓库所有者账号、项目公开域名）随案例保留，这是发布渠道本身的信息；姓名、邮箱、手机号等个人信息一律禁止出现（扫描口径见 `rules/05` 与 `SENSITIVE-INFO-AUDIT.md`）。
