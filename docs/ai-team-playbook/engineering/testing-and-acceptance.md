# 测试与验收手册

> 什么样的验收算「验过了」。来源：dtk 各轮上线的验收实践。规则层见 `rules/03`，本篇是可直查的方法手册。

## 三条验收原则

### 1. 量化口径先行，先修口径再修问题

性能类问题在动手修之前，先把验收口径写死。例：dtk 大文本卡顿的验收口径定为 **2000 字 ≤500ms、5000 字 ≤1500ms 且耗时曲线近线性**——注意是「先修测试口径，再修性能」，防止修完之后拿一个宽松口径自我宣布达标。

历史实测参照（修后，取自当时测量环境）：2000 字约 85ms、5000 字约 150~180ms。换环境按同法重测。

### 2. 不变量写进自动化测试

凡「无论怎么改都不能破」的性质，写成机器断言，不靠评审盯。dtk 的两条示范：

- **幂等**：对已排好的文本再执行一次排版，输出逐字节不变；零改动时不产生撤销栈垃圾；
- **零内容丢失**：处理前后剥离全部空白与控制指令后，可见字符序列必须逐字节一致。

另有版本同步门禁：故意改错版本号、删预加载、改默认文本一个字，三类破坏必须全部立刻红（对抗性自验——门禁本身也要被测试）。

### 3. 独立质检，用独立探针

- 质检者独立于实施者，**自建探针和样本**复证，不用实现方的用例：
  - 双击定位修复后，质检用独立探针对 **85 个格子逐格双击，0 漂移**才算过；
  - 排版功能由质检自建 8 组样本 + 47.6 万字符脏样本复证零丢失与幂等；
- 换干净目录重跑全量测试（防止「在我机器上能过」）：历史口径 52 单测 + 78 E2E、88 单测 + 99 E2E，换目录重跑全绿；
- 质检结论只写三态：通过 / 有条件通过（列条件）/ 不通过，并附证据。

## 双引擎对账

关键规则引擎改动（如标点占格），用**两个独立实现的引擎**跑同一语料对账，结果一致才采信——单引擎自测绿只能证明「代码按自己的理解跑通了」，不能证明理解正确（见 `cases/case-dtk-01`）。

## 全面审计方法论（全面剖析 → 第三方整合）

对成熟项目做全面质量审计的可复用流程，定稿于 dtk「全面剖析 → 20 条缺陷修复」轮：

1. **双方独立剖析**：两路成员互不沟通，各自对同一 codebase 产出缺陷清单——独立视角才能抓到对方的盲区；
2. **第三方整合**：由未参与剖析的第三方合并去重，产出统一的分级清单（P0/P1/P2），每条带证据与修复建议；
3. **分批实施**：按「**同区域同批、最高风险单独一批**」分批，每批全量测试过关再进下一批，批次之间风险隔离（20 条清单当年分五批实施）；
4. **反例纪律**：清单里的理论推断项（如「打印行间隙有问题」）被真实证据否决就从清单撤销，不为了凑数而修。

## 测试可移植化

教训来源：dtk 20 条缺陷轮曾出现「测试脚本换台电脑就跑不了」。规矩两条：

- 测试脚本**内置静态服务**（自起服务、自开端口），不依赖本机已装的任何东西；
- **去绝对路径**：一切路径相对仓库根解析，克隆到任何机器即可跑。

这是「换干净目录重跑」质检法的前提——测试自己不可移植，独立质检就无从谈起。

## 测试资产随功能沉淀

功能上线的同时，其测试成为永久资产：dtk 从 26 单测 + 28 E2E 起步，逐轮增长到 88 单测 + 99 E2E。每轮新功能必须带新用例，每轮修复必须带回归断言（如「修复双击偏移」必须补前/中/后段多位置断言）。

## 已知遗留的披露纪律

上线报告里**如实披露不阻塞的遗留项**，不藏起来。示范（真实披露格式）：

- 🟠 键盘直输 emoji 的过滤暂未拦截（粘贴/导入/恢复三路径已拦截），刷新后自动修正，建议后续补兜底；
- 🟡 安全响应头需部署后线上核实一次。

「已上线」与「完美无缺」是两回事，后者不需要假装。
