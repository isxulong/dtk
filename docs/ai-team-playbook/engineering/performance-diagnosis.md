# 性能诊断手册

> 两个对照案例凝练出的方法论：一次真病灶在代码（粘贴卡顿，`cases/case-dtk-03`），一次真病灶在网络（白屏，`cases/case-dtk-05`）。方法论完全相同——**先分段实测定位，再谈优化**。
>
> 数值口径说明：本文性能数值均取自当时的测量环境（测试机型、网络路径随轮次不同），仅作口径参照；换环境按同法重测，不照抄数值。

## 方法论：四段定位法

把「用户感觉到慢」拆成可分别测量的段落，逐段拿数字，不猜。白屏问题的四段拆分示范：

1. CDN/网络段：HTML 响应时间、缓存命中（`Cache-Control`、`CF-Cache-Status`）；
2. 模块瀑布段：各 JS 请求的开始/结束时间，是否串行、几级串行；
3. 脚本求值段：模块执行耗时；
4. 渲染段：核心 DOM 构建耗时。

实测结果：渲染段 400 格只要 6~20ms（双方独立测量一致排除），病灶在 1、2 段——**渲染层无辜**。不实测的话，很容易在渲染层白做「虚拟化」之类的无用功（该方案被终裁明确否决：无优化空间）。

## 六条规则

### 1. 理论推测必须让位于可复现实测

- 「打印行间隙有问题」是打印预览里的理论推断，真实打印件完美 → 不修；
- 反面的教训同样重要：双击定位修复前，旧测试 **175 个测试点零偏移全绿**，bug 仍漏网到真机——测试样本没覆盖「存档恢复产生 `<br>`」这条真实路径。**教训：测试样本必须覆盖全部数据来源（手输 / 粘贴 / 导入 / 存档恢复）**；该修复的正面验收口径是质检官独立探针对 **85 个格子逐格双击、零漂移**，而不是沿用旧的测试点计数（见 `cases/case-dtk-02`）。

### 2. 单变量原则，实验臂只改一个东西

蓝方的「-54% 收益」实验臂实际捆绑了两个变量（拆锁 + 预加载），被红方用其自家瀑布数据证伪——**归因错误比没有数据更危险**，它会把后续资源引向错误的优化点。设计 A/B 实验时，逐变量列出实验臂与对照臂的差异清单。

### 3. 基线必须可复现，且用对方数据交叉验证

红方「白屏 4~8 秒」的基线与蓝方可复现实测（1.6~2.9 秒，且是更差网络路径）差 2~3 倍 → 否决。报基线时必须写明：测量环境、网络路径、样本量、是否可复现。

### 4. 收益外推标明边界

测试环境的收益不直接承诺到用户真实网络：「国内到 Cloudflare 的真实路径无法在测试环境复现，上线后需真机回归」。目标写成带条件的口径（如「冷启动首格 ≤1.5 秒（Fast 4G 实验线）」），不承诺达不到的 <1 秒。

### 5. 找到「必须第一个拆的锁」

多个优化项之间常有硬依赖：onload 锁不拆，其它所有优化的收益都到不了用户（「只加 preload 不拆锁 = 零收益」被实测反证成立）。改动顺序是设计的一部分，写进终裁。

### 6. 性能数据同源对账

收益数字至少要两方独立复测量级吻合才交付：质检复测「HTML 到达→首格」646ms→344ms（-46.7%），与蓝方真网实测 -54% 同量级，且机制解释得通（恰好消除一个串行网络往返）——**数字吻合 + 机制吻合**双满足才报给用户。

## 代码层性能的两个具体教训

1. **先怀疑强制同步布局（reflow）**：dtk 粘贴 5000 字 34 秒的 O(N²)，真实瓶颈是 `innerText` 每次读取强制 reflow，而不是直觉上的「网格重建太多」。改 `textContent` 后降到 125ms。**先 profile 出热点，再决定重构范围**——别凭结构直觉重写。
2. **确定性方案的性能上限要先实测再担心**：「一键排版会不会很慢需要等待弹窗」——实测 0.12ms/2781 字，10 万字病态上限 <20ms，弹窗需求自然消失。**禁止人造延时**：处理快于肉眼一帧时，「处理中」状态不可见是自然结果，不许为了让用户「感知到在工作」而故意加延时。
